# 本文档用于储存开发者的个人构思以及理解

当前先构建最基本的学生模型体系，把"学生"这个最基本的模型定义清楚。
- 相关模块：doc\modules\kaleido-profile.md

## 定位（修正）

本模块是**学生评价模型**，不只是学生信息表。它同时定义两件事：

1. **学生是谁**：类型层 + 属性层。
2. **如何评价这个学生**：评价框架层（评价维度 → 指标 → 观测点 → 评分标准）。

## 三层结构

- **类型层**：障碍分类体系（视力障碍 / 听力障碍 / 智力障碍 / 自闭症），带 parent 与 tags，可扩展、可组合（支持多重障碍）。
- **属性层**：障碍程度、认知等级、感官偏好、康复目标、学习节奏，以及动态能力基线。
- **评价框架层**：不写死，由引擎按"类型 + 属性"实例化出个性化评价框架（指标清单 + 权重 + 观测频率 + 评价方式）。

## 数据来源（重要）

本模块不采集课堂数据，也不自动"给评价"。三类东西要分清：

- **静态属性**（障碍类型、程度、认知等级等）：建档时由教师/家长/入学评估**录入一次**，系统无法自动获知。
- **评价框架**（评什么、怎么评）：由配置与规则引擎生成，是**标尺**，不是数据。
- **动态评价数据**（课堂参与、答题、行为表现、康复进展）：随教学持续采集，归 **`kaleido-loop`**，不属于本模块。

因此"画像自动生成"不准确：系统自动完成的是"从已录入属性推导评价框架与适配约束"，属性本身仍需建档录入。特教评价也不能只看答题自动评分，需前后测、课堂观察、教师反馈、家长评价等多源数据（量化 + 质性）。

## 职责边界

- 本模块是**本体 / 业务层**，不是数据层。
- 本地 JSON 的读写、加锁、内存索引由 `kaleido-vault` 负责；本模块只通过 `repository` 委托它持久化。
- 不负责"把画像递交给存储"，而是负责输出**标准化的"学生实例 + 评价框架"**。

## 上下游

- **下游**：向 `forge` / `match` / `loop` 输出标准化的学生实例与评价框架，作为整个闭环的输入契约。
